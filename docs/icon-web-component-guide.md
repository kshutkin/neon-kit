# Icon Web Component Guide

Working notes for future changes around `<neon-icon>`, `@neon-kit/icons`,
and the upstream libraries this repo uses to implement native custom
elements.

## Current Implementation

`<neon-icon>` lives in `web-components/src/icon.jsx`.

- Importing `@neon-kit/web-components/icon` registers the autonomous
  custom element as a side effect.
- The element renders into Light DOM, not a shadow root. This follows
  `docs/adr/0001-rendering-mode.md` and keeps styling/inheritance simple.
- The component uses `defineElement('neon-icon', [attributes(...)], renderIcon)`.
  That means the tag name is fixed at module import time.
- The public reactive props are created with `props()`:
  `name`, `aria-label`, `title`, and `icon`.
- `name`, `aria-label`, and `title` reflect to attributes with a local
  `reflectedString` descriptor. Unlike Slimlib's normal `stringAttribute`,
  assigning `''` removes the attribute to preserve legacy behavior.
- `icon` is a property-only override. It is not reflected to an attribute.
  If `icon` is non-null, it wins over `name`.

Rendering flow:

1. `renderIcon()` creates reflected props and a private `loadedSig`.
2. An effect watches `state.icon` and `state.name`.
3. If `state.icon` exists, async loading is ignored and `loadedSig` is cleared.
4. If `name` exists, the component calls
   `import(/* @vite-ignore */ \`@neon-kit/icons/${name}\`)`.
5. A monotonically increasing `token` prevents stale async imports from winning
   after rapid `name` changes.
6. The returned render function chooses `state.icon || loadedSig()`.
7. `IconSvg(def, label)` builds a real SVG node with `@slimlib/jsx`'s `svg()`
   namespace helper.

SVG output:

- Root attributes start with `xmlns` and `viewBox`.
- Variant-level `def.attrs` are copied next.
- `width="1em"` and `height="1em"` are always added. Size via CSS
  `font-size` on the host or ancestor.
- With `aria-label` or `title`, the SVG gets `role="img"` and an inline
  `<title>`.
- Without a label, the SVG gets `aria-hidden="true"`.
- Each `def.paths[]` entry becomes a `<path d="...">` with optional path attrs.

`web-components/src/svg-icon.jsx` is a smaller helper for internal component
icons. It also uses `svg()` but does not define a custom element, does not
lazy-load icon modules, and always emits `aria-hidden="true"`.

## `@neon-kit/icons`

The icon package is generated from Heroicons. The runtime data shape is:

```js
{
  viewBox: '0 0 24 24',
  attrs: { fill: 'none', stroke: 'currentColor', 'stroke-width': '1.5' },
  paths: [{ d: '...', attrs: { ... } }]
}
```

Important package behavior:

- Four variants exist: `outline`, `solid`, `mini`, `micro`.
- Subpath modules are the tree-shakeable path:
  `@neon-kit/icons/<variant>/<name>`.
- Aggregate imports exist at the root and per variant, but they pull more into
  the module graph.
- `serialize(iconDef, opts?)` is the DOM-less equivalent of `<neon-icon>` and
  tests assert the custom element output stays structurally aligned with it.
- Icon source files are generated by `icons/scripts/build-icons.mjs`.
  Do not hand-edit generated icon modules unless the request is explicitly
  about generated output.
- To add icons, edit the generator manifest and run
  `pnpm --filter @neon-kit/icons run gen`.

## Dynamic Import Caveat

The element deliberately uses:

```js
import(/* @vite-ignore */ `@neon-kit/icons/${name}`)
```

This keeps the component runtime-agnostic for environments that can resolve
bare specifiers directly, such as Node ESM or browsers with an import map.

Bundlers cannot analyze or rewrite that ignored dynamic specifier. In Vite
browser tests and the docs site, the repo uses an adapter pattern instead:

- Build a name-to-loader map with `import.meta.glob(...)`.
- Watch for `<neon-icon name="...">`.
- Assign `el.icon = mod.default`.

See `site/icons.js` and `web-components/tests/icon.spec.mjs` for the current
hydrator. When `name` changes on an existing element, clear `el.icon = null`
before resolving the new icon, otherwise the property override keeps winning.

## Slimlib Libraries

### `@slimlib/element`

Used for custom element lifecycle and attribute/property wiring.

- `defineElement(tag, middleware, render)` creates and registers immediately.
- `createCustomElement(...)` creates an unregistered constructor. Use this when
  a component needs exported constructors or custom tag registration.
- `props(initial)` must be called synchronously inside the render callback. It
  installs host accessors and returns a reactive proxy.
- Existing pre-upgrade property values are adopted by `props()`.
- `attributes(config)` takes `[parse?, serialize?]` tuples.
- A parse function makes the attribute observed.
- A serialize function reflects prop writes back to the attribute. Returning
  `null` removes the attribute.
- Reflection is an effect, so reflected keys must also be declared with
  `props()`.
- `connectedCallback` runs the render once per mounted period, then emits
  connect events.
- `disconnectedCallback` waits a microtask before real unmount so same-task
  detach/reattach moves do not tear down state.

Sharp edge: if a test or caller expects cleanup synchronously right after
`el.remove()`, do that work in `onDisconnect`, not an `onMount` cleanup.

### `@slimlib/store`

Used for reactive props and async-loaded icon state.

- `signal(value)` returns a callable getter with `.set(value)`.
- `state(object)` returns a proxy with fine-grained property tracking.
- `effect(fn)` tracks reads and reruns after the scheduler flushes.
- Default effect scheduling is microtask-based and batched.
- Avoid `flushEffects()` in components. Let normal effect scheduling run and
  adapt tests around user-observable settled state unless a truly synchronous
  public contract requires otherwise.
- `EffectOptions.EAGER` can make the first run synchronous, but later reruns
  still use the scheduler.

For `<neon-icon>`, tests currently wait for async import and paint to settle
instead of relying on synchronous repaint from `name`.

### `@slimlib/jsx`

Used to create real DOM nodes, not a virtual DOM.

- Components run once; updates happen through reactive functions/effects.
- `render(factory, container)` inserts real nodes and returns a disposer.
- JSX event props use `on:event`.
- Attribute/property assignment uses a prototype-setter heuristic. Use
  `prop:` or `attr:` prefixes if the heuristic is wrong.
- Function children become reactive ranges with comment anchors.
- SVG must be created inside `svg(() => (...))` because JSX children are built
  bottom-up and cannot infer namespace from a parent `<svg>`.

Known local gotcha from `web-components/SLIMLIB-NOTES.md`: function-child
replacement had problems for `null` to `<svg>` swaps in earlier icon migration
work. If touching whole-subtree icon replacement and NotFoundError appears,
prefer an imperative effect that calls `host.replaceChildren(node)` while still
building the SVG with JSX.

## Test Surface To Preserve

`web-components/tests/icon.spec.mjs` covers:

- registration as `neon-icon`;
- property rendering via `el.icon`;
- name-based loading via the test hydrator;
- `icon` property precedence over `name`;
- clearing `icon` falls back to `name`;
- stale async import protection on rapid `name` changes;
- warning and empty render for bad names;
- fixed `1em` SVG size;
- accessible label handling;
- structural parity with `serialize()`;
- property-to-attribute reflection and empty-string removal;
- no output when neither `name` nor `icon` is set;
- icon defs with omitted `attrs` still render.

Useful verification commands:

```sh
pnpm --filter @neon-kit/web-components test -- icon
pnpm --filter @neon-kit/web-components test:types
pnpm --filter @neon-kit/icons test
```

Avoid `pnpm pack` locally in these packages. Their `prepack` uses `pkgprn`
with flattening, and the existing project notes call that destructive to the
source tree.
